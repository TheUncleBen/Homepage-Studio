## Matching failures and confirmed cause

Both native jobs use Chromium/Headless Shell **156.0.8078.4**, Playwright browser
revision **1248**, and fail at the same unchanged 10-second active-panel checks:

- `browser/specs/dashboard.spec.mjs:164`: the panel identity does not advance
  after the independent six-step touch-header swipe.
- `browser/specs/stack-picker.spec.mjs:89`: the panel identity does not advance
  after the shared eight-step touch-title swipe.

Both helpers send actual Chromium touch events through `Input.dispatchTouchEvent`.
They have no architecture-specific branch. The complete job logs establish the
matching symptom; a separate local reproduction establishes the event sequence.

The two unchanged browser cases also failed locally against the `26f6cc5`
production build, whose Studio source matches this candidate. The real pointer
trace shows implicit capture on the title's child element, followed by transfer
to the stack shell when horizontal dragging starts. The child's
`lostpointercapture` event is delivered while the shell already owns capture for
that pointer. The review-added watchdog matches only the pointer identity and
incorrectly treats this legitimate transfer as cancellation. It clears the drag,
so the later pointer-up cannot advance the stack. This is a regression in the
reviewed product code, not a flaky-test or architecture diagnosis.

The owner-aware correction is now integrated as
`d68d261e03422b0daf1ce7a40dfa252270c4193a` (reviewed patch
`db2f01888cca25a41797ed009e3d7801d1ea421e`). It preserves the intended capture
transfer and all real cancellation paths. Both original failing swipe cases are
byte-unchanged. The corrected local production build has passed the complete
**38/38 Chromium suite with zero retries, skips or flaky results**, including
the strengthened held-title arrangement case. Its prior 37/38 local invocation
