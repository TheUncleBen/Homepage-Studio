# Working on Homepage Studio

## Product contract

Maintain the complete controlled Homepage-derived React application in `homepage/`. One application image contains the public controller and internal native workers. All four panel kinds—service, serviceWidget, informationWidget, and bookmark—must be independently placeable and stackable. A fresh dashboard is empty. Preserve the restrained gray/white and eggplant default while supporting per-dashboard dark/light/device appearance, accent selection, and native custom CSS. Keep these preferences in that dashboard's settings.yaml; do not introduce a separate theme store.

Use one visible Play/Pause control per stack, passive progress indicators, touch swipes, horizontal desktop drag/trackpad input, and focused Left/Right keys. A successful manual navigation while playing resets that stack's hold to max(normal interval, manual hold), default 30 seconds. The first automatic advance occurs when the hold ends, then normal timing resumes. Paused stacks stay paused. Playback and temporary drag offsets never persist or create snapshots. Respect interactive native content, reduced motion, document visibility, and offscreen/editing timer suspension.

Keep native panel hosts stably keyed across geometry changes, stacking, navigation, and unstacking. Do not replace native widgets with mock implementations. External Docker/Kubernetes definitions stay with their native labels/annotations; only layout and visibility are Studio-owned.

The stack title picker is an intentional short click/tap or keyboard action. Swipes, horizontal/vertical drags, long presses and context menus must not open it. Preserve a quiet closed presentation, deliberate selection, focus return, keyboard/Escape behavior and existing slide gestures. It cannot replace or duplicate the agreed Play/Pause-only transport controls.

## Independent dashboards

One exact accepted host/origin serves independent dashboards at configurable single-segment slugs. Every dashboard owns all nine native files, panel identities, layout, stacks, appearance/CSS/JavaScript, discovery cache, revision state, journal and snapshot history. Registry identity is immutable; a slug is only an address. The original dashboard remains in its existing volume paths. New dashboards use UUID-keyed subdirectories. Create, duplicate, rename/change address, archive and restore through the revision-checked registry. A duplicate is independent from its source; archived addresses remain reserved and data remains recoverable.

Each active dashboard gets a separate native worker process with its own configuration and browser request context. Native URLs, data caches, cookies and local browser preferences must carry the selected dashboard identity. Workers bind only loopback and inherit UID 1000. Bound worker count/startup/idle duration, drain changed contexts, recover child crashes on a subsequent request and close workers during shutdown. Runtime defaults are 8 workers, 600 idle seconds and 30 startup seconds.

Global `/__studio/application-ready` checks the registry, shared storage and packaged native runtime without starting a worker. Docker health uses this endpoint. `/[slug]/__studio/ready` checks the selected dashboard and native worker. Broken default configuration must not fail global health, healthy named dashboards or shared build assets. Do not add proxy/DNS/TLS management or treat a path slug as an access-control boundary. Studio sign-in (owner direction, 23 Oct 2026; docs/AUTHENTICATION.md) lives in `server/auth/` and is enforced only in the controller: default deny, `requiredLevel` in `server/auth/access.mjs` is the single list of what View and Arrange may reach, and every new `/__studio/` endpoint is administrator-only unless deliberately added there. Never forward the session cookie to workers, never re-enable Homepage's native auth or MCP endpoint while sign-in is on, and keep widget settings, raw files, custom CSS/JS, import/export and access lists administrator-only. With `STUDIO_AUTH=off`, trusted editor users on the same origin manage the deployment and external access control is the owner's responsibility.

## Data and compatibility

The controller owns each dashboard's nine managed native files and state.json. Preserve unknown native fields, comments where the YAML AST permits, literal environment/file references, stable panel identities, revision checks, recoverable transactions, and 25-snapshot default retention. Validate before creating snapshots. Do not create new integration adapters without a concrete product decision.

Structured edits must send only changed keys so an unrelated edit cannot delete an unknown null value or rewrite a native default. Complete portable imports require an explicit confirmation and the target's current revision; selecting a file is not a write. Normal JSON requests remain bounded to 2 MiB; only the complete dashboard import endpoint permits 40 MiB, with each imported file/state still limited to 2 MiB. Snapshot ordering must survive equal timestamps, backward clock changes, and restart.

Keep board/native data paired by their nine-file configuration revision. Never resolve a new same-type locator against old native data. Preserve healthy hosts and local drafts while a refresh is pending, retain the draft's original revision on an external update, and distinguish a committed write from a failed subsequent refresh. Native MCP writes are outside the single-writer contract and remain disabled in the supplied deployment.

The original Homepage baseline and build toolchain are pinned in upstream.lock.json. Edit the tracked `homepage/` source directly; see docs/NATIVE-SOURCE.md. The root Dockerfile copies this source and runs frozen dependency installation, the production build and asset compression; the native audit, redirect-security check, lint and full native tests run in the required `native-checks` CI job that every image build depends on. No upstream fetch, overlay generation or companion container participates in the build. Keep controller/native protocol, upstream provenance and build revision consistent inside the image. Preserve AGPL/GPL, historical grants, font notices and corresponding source.

Never commit runtime configuration, credentials, private project documentation, state, snapshots, downloaded dependency trees, generated build trees, or test data from real infrastructure. Synthetic examples must use reserved example domains.

## Verification and releases

Document changes, tests actually executed, remaining limitations, and the next concrete step. Do not carry historical prototype test results forward as evidence for this renderer. A passing controller test is not browser/device testing, and parsing deployment YAML is not container acceptance.

Follow docs/RELEASES.md. The engineering workflow may build and deliver a requested candidate without an owner-only dispatch or candidate environment approval. A trusted default-branch push containing [deliver-candidate], or a deliberate manual candidate dispatch, requests retention of the fully qualified application image. Other pushes validate without publication. Keep source/run tags unique, verify both native architectures, the complete image and single corresponding-source archive, and report anonymous availability separately from build success. Official versions remain YYYY.MM.DD, immutable, and owner-approved for the exact artifact set after human testing. Never move an existing official tag, introduce a moving preview image channel, or rebuild approved image bytes during promotion.

Before completing work, update relevant architecture/deployment documents, and VERIFICATION.md when the verification commands, gates or known limitations change. Keep dated run logs, review records and qualification history out of this repository: they belong in the owner's separate private canonical project record; reconcile the current status and handoff there when that destination is available. Keep private links and owner infrastructure out of this public repository.
